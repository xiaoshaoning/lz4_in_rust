# lz4_in_rust

A **structure-preserving port of [LZ4](https://github.com/lz4/lz4) to Rust** (upstream v1.11.1),
with two non-negotiables:

- **zero `unsafe`** — the whole crate is `#![forbid(unsafe_code)]`; every read and write is
  bounds-checked, so any input (including corrupt or hostile blocks) yields `Err`, never a
  panic, overrun or hang;
- **byte-identical output** — for the same input the compressed stream is the same bytes the C
  library produces, not merely "a compatible stream". Any diff is a porting bug, so the tests
  are equality assertions instead of approximation checks.

The C implementation buys its speed with unchecked pointers; this port keeps the same speed
shape with explicit index invariants instead (see `docs/DESIGN.md` §2). Speed is measured, not
assumed: on match-heavy data the safe decoder runs at 0.6–0.7x of C, on long-match data it
beats C (memmove instead of an 8-byte wildcopy).

**`0.0.x` is a pre-release.** It covers the block codec, the parallel engine, the frame
format and a working command line tool; high-compression levels (`-2..-12`) are what `0.1.0`
waits for.
Until then the API may change between `0.0.x` releases. The frame layer is whole-buffer
(no `Read`/`Write` adapter yet), has no dictionary support, and a *linked* frame it writes
does not actually link blocks — see `docs/REVIEW.md`.

| `par` | parallel block engine + adaptive worker policy; `compress_each` streams blocks in order | — (new) | ✅ output independent of thread count |
| `frame` | LZ4 frame format: descriptor, blocks, both checksums, linked + independent, skippable frames; **streaming** via `Read`/`Write` | `lib/lz4frame.c` | ✅ our frames are byte-identical to C's and `lz4 -d` reads them |

| `cli/` (`lz4r`) | command line tool: files, pipes, `-1..-12`, `-B#`, `-T#` | `programs/` | ✅ **GPL-2.0-or-later** (separate crate) |

## Command line

`cargo build --release -p lz4r` gives `lz4r`, a `.lz4` tool that interoperates with the
reference `lz4` in both directions:

```sh
lz4r file.txt              # -> file.txt.lz4
lz4r -d file.txt.lz4       # -> file.txt
lz4r -9 -B7 -T0 file.txt   # level 9, 4 MiB blocks, auto threads
lz4r -c file.txt | lz4 -d  # pipes
lz4r -t file.txt.lz4       # integrity check
```

It is a **separate crate under GPL-2.0-or-later**, because it is a port of upstream
`programs/`; the library stays BSD-2-Clause. It streams: memory stays bounded by one batch
of blocks, so file size is not a constraint.

## Build and check

```sh
cargo test --workspace                       # 75 tests, no C toolchain needed (fixtures are committed)
cargo test --release                         # same, and much faster on the big roundtrips
cargo clippy --all-targets && cargo fmt --check
```

The differential tests run against fixtures generated by the C library itself
(`tests/fixtures/*.raw` + `*.lz4`). To also check the *other* direction — that C can decode
what we produce — build the oracle and point the tests at it:

```sh
tools/build_oracle.sh /path/to/c-lz4       # or, on Windows:
gcc -O2 -I/path/to/c-lz4/lib -o target/c-oracle tools/c_oracle.c \
    /path/to/c-lz4/lib/{lz4,lz4hc,xxhash}.c

LZ4_C_ORACLE=target/c-oracle cargo test
LZ4_C_ORACLE=target/c-oracle LZ4_FUZZ_ROUNDS=150 cargo test --release   # and fuzz it
```

`LZ4_FUZZ_ROUNDS` adds random cases to the differential sweep
(`tests/fuzz_diff.rs`): every data shape (one long run, short cycles, text, noise, mixed,
random runs) at every boundary size (12, 13, 64 KiB, the 64 KiB table switch, ...), each
checked four ways — our block bytes are identical to C's, C decodes our block and our
frame, and we decode C's block (fast *and* high-compression) and frame. A failure prints
its seed and case, so it reproduces with `LZ4_FUZZ_SEED=...`.

## Measuring

```sh
cargo run --release --example bench -- <file>            # one block, block API
cargo run --release --example parallel_probe -- <file>   # Single / Fixed(2|4|8) / Auto
target/c-oracle bench <file>                             # the C reference, same machine, same API
```

Report the **ratio** between the two, on the same machine, in the same run: a laptop's clock
drifts by up to 3x between runs, so absolute numbers alone are not comparable. Everything in
`docs/DESIGN.md` was measured that way, and the two strategies that looked obvious but lost
(per-length copy ladder, windowed slices) are listed there so they are not retried.

## How it is tested

- **Equality against C** — compressed bytes, decompressed bytes, XXH32 digests.
- **Corrupt input** — every truncation point and every single-bit flip of a compressed block
  must produce `Err`; `dst` is pre-filled with a pattern, so any reliance on unwritten memory
  shows up as a mismatch.
- **Roundtrip sweep** — sizes 0..600 plus the sizes around the decoder's fast/slow boundary,
  with repeats that exercise every match-offset bucket.
- **Thread invariance** — `Single`, `Fixed(1,2,3,8)` and `Auto` must produce identical blocks.
- **Differential fuzz** — the sweep described above, over generated data rather than fixtures.
- **Portability** — the suite also runs on 32-bit (`i686`), the crate compiles for a
  big-endian target, and Miri (nightly, in CI) checks the small-input logic for undefined
  behaviour. `#![deny(missing_docs)]` keeps the public surface documented.
